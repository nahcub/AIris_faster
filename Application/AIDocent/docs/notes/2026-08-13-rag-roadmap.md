## 0. 먼저 정리할 것 — 우리에게 RAG가 무엇을 더 주는가

⚠️ **우리는 이미 retrieval을 하고 있다.** `ArtworkRecognizer.recognize()` → `Artwork` → `setArtwork()` →
`decodeSystemPrompt()`가 그 작품의 `description`을 시스템 프롬프트에 프리필한다.
이건 **정확한 key lookup**이라 임베딩 검색보다 정확도가 높다. 이 자리를 RAG로 대체하면 손해다.

그러므로 RAG가 붙어야 할 자리는 **"눈앞의 작품 1점 밖"** 이다:

| 관람객 질문 유형 | 지금 답할 근거 | RAG가 주는 것 | 검색 단위 |
|---|---|---|---|
| "이 그림 뭐야?" | ✅ 있음 (인식된 작품 description) | 없음 — 건드리지 말 것 | — |
| "홀바인 다른 작품은?" | ❌ 없음 → 환각 | 같은 `author`의 다른 작품 | **작가 프로필** + 메타 필터 |
| "이 작가 어떤 사람이야?" | ❌ | 그 작가의 전시 내 작품 전반 | **작가 프로필** |
| "이 시대 독일 회화는 어떤 특징이야?" | ❌ | 같은 `school`/`date` 대역 | **사조 프로필** |
| "이런 분위기의 다른 그림 있어?" | ❌ | 의미 유사 작품 | **작품 청크** |
| "저 카펫이 왜 저렇게 구겨져 있어?" | 부분적 | 기법·도상 관련 다른 기록 | **작품 청크** |

즉 **우리 RAG의 정체는 "이 전시의 소장 기록을 근거로 한 확장 질의응답"** 이다.

### RAG의 가치는 "모르는 걸 알려주기"보다 "지어내는 걸 막기"다

Gemma는 사전학습으로 "르네상스가 뭔지" 정도는 이미 안다. 그런 일반 지식을 검색해 넣는 건 이득이 적다.
RAG가 실제로 값어치를 하는 건 **모델이 알 수 없는 구체적 사실** 쪽이다:

- ❌ "르네상스란?" → 모델이 이미 안다. 검색해도 이득 적음
- ✅ "이 전시에 홀바인 작품이 또 있어?" → **우리 코퍼스에만 있는 사실**
- ✅ "암굴의 성모는 누가 그렸어?" → 대조군이 **카라바조**라고 틀렸던 지점(CLAUDE.md 품질 문제 #2).
  근거 레코드가 붙으면 잡힌다

⚠️ **RAG가 기존 문제를 악화시킬 수 있다는 것도 미리 적어둔다.** CLAUDE.md에 기록된
**앵무새(parroting)** 문제 — 두 모델 다 `description`을 그대로 복창한다 — 는 컨텍스트를 더 넣으면
더 심해지는 게 자연스럽다. "RAG를 넣었더니 근거는 늘었는데 도슨트 화법은 죽었다"가 가장 유력한 실패 시나리오다.
**LoRA(화법) × RAG(근거)의 상호작용**이 이 단계의 진짜 연구 질문이다.

`app/src/main/assets/art_metadata.json` — 18MB

### 1-2. ★ 실제로 쓸 것은 "전시" 부분집합 (~300점) — 결정 1

21,382점 전체를 다루는 건 비현실적이고, **평가가 성립하지 않는다.** 골드셋 30~50문항으로 21,382점을
평가하면 커버리지가 0.2%다. 300점이면 같은 문항 수로 촘촘한 평가가 된다.

**얻는 것**

- 골드셋이 의미를 갖는다 (위)
- 인덱스 재구축이 시간 → 초. 임베더·청킹·텍스트 포맷 실험(§5-5)을 하루에 여러 번 돌릴 수 있다
- **작가·사조 프로필이 성립한다.** 전체 코퍼스의 3,281작가는 대부분 작품 1~2점짜리라 프로필이 빈약하다.
  큐레이션된 전시라야 작가당 충분한 작품 수가 모인다
- 제품으로서 정직하다 — 실제 도슨트는 "서양미술 전체"가 아니라 특정 전시를 안내한다

**잃는 것 (정확히 알아둘 것)**

- ⚠️ **Phase 2 게이트가 쉬워진다.** ~350청크에서는 웬만한 임베더도 Recall@3이 잘 나온다.
  다만 한 전시 안의 작품들은 서로 비슷해서(같은 시대·지역) **구별이 오히려 어려운** 면이 있다.
  쉬워지는 만큼 어려워지는지는 Phase 2에서 실측할 일이다
- ⚠️ 로드맵 초안의 "24k도 전수 스캔으로 충분하다"는 실측은 **온디바이스 RAG로서 나름의 기여**였는데,
  300점이면 그 주장이 사라진다(누구나 되는 크기). → 아래 이중 인덱스로 회수한다

### 1-3. 크기를 실험 변수로 만든다 (이중 인덱스)

두 축은 분리 가능한 손잡이다. **같은 스크립트로 인덱스 두 개를 뽑아 골라 쓴다.**

| 축 | 코퍼스 | 무엇을 재나 |
|---|---|---|
| **제품 시나리오** | 전시 ~300점 | 골드셋, 품질 평가, 데모, 4셀 비교 |
| **스케일 증거** | 전체 21,382점 | retrieval latency, `mem_peak`, 대규모 Recall |

이건 **이 프로젝트가 이미 두 번 쓴 패턴**이다. `ModelCatalog`가 모델 파일을 스캔해 재빌드 없이
골라 쓰게 했듯, `IndexCatalog`(§5-1)가 인덱스 파일에 똑같이 해준다. 인덱스 두 개를 push해두고 고르면 끝.

> ⚠️ **그래서 `build_chunks.py`는 처음부터 "전체 → 부분집합 필터" 파라미터를 받게 짤 것.**
> 300 전용으로 짜두면 나중에 다시 짜야 한다. 부분집합 파라미터가 있으면 스케일 축이 나중에 **공짜로** 생긴다.

### 1-4. 어떤 300점을 고를 것인가

⚠️ **무작위 300점은 안 된다.** 무작위면 작가·사조가 다 흩어져서 "홀바인 다른 작품은?"에 답할 근거가
코퍼스에 없어진다 — RAG를 붙이는 이유 자체가 사라진다. **응집된 전시**여야 한다.

제약이 하나 이미 걸려 있다: 현재 `FixedArtworkRecognizer`가 **Darmstadt Madonna**를 반환한다.
눈앞의 작품이 그것이므로 **전시는 그 작품을 포함하고 그 주변으로** 짜여야 파이프라인 전체가 이어진다.

자연스러운 후보:

```
"북유럽 르네상스" 전시
  school ∈ {German, Flemish, Dutch}
  date   ∈ 1450–1550
  → Holbein, Dürer, Cranach, Bosch, Bruegel, van Eyck ...
  → Darmstadt Madonna 포함 ✅
```

### 1-4-1. ✅ 실측·확정 (08-13) — `northern-renaissance-295`

전시 제목: **Devotion and Likeness** — *Painting North of the Alps, 1450–1550*
(종교화 65% + 초상 22% = 87%라는 실제 구성에서 나온 제목. ⚠️ **내부 ID `northern-renaissance-295`는
표시 제목과 무관하게 고정** — 벤치 레코드의 `index` 필드에 남는 값이라 제목이 바뀔 때마다 따라 바뀌면
과거 레코드와 대조가 안 된다. `model` 필드를 다루는 방식과 같다.)

필터를 실제로 돌려 **295점 / 26작가**로 확정했다. 파일 두 개로 나눠 뒀다:

| 파일 | 역할 |
|---|---|
| `datasets/exhibition_ids.json` | **출처 기록** — 필터 조건 + 선정 ID 295개 + 표시 제목. ⚠️ 캡 규칙에 동점이 생기면 재현이 흔들리므로 ID 목록 자체를 동결 |
| `datasets/exhibition_northern-renaissance-295.jsonl` | **작업용 추출본**(425KB) — 선정 295점의 전체 메타데이터. `id/title/author/type/technique/school/date/**year**/description` |

추출본을 따로 두는 이유: 청킹·프로필·골드셋 작업이 **18MB 원본을 로드하고 필터를 재적용할 필요가 없어야**
한다(특히 무인 배치 작업의 입력은 자기완결적이어야 한다). `year`는 `date` 자유 텍스트("1526 and after 1528")에서
파싱해 미리 넣어 뒀다 — 사조 프로필이 이 값으로 묶인다. 추출본은 **파생물**이라 원본이 바뀌면 재생성하면 된다.

```
school ∈ {German, Flemish, Dutch}, year ∈ [1450, 1550]
author 가 "UNKNOWN"으로 시작하면 제외      ← 작가 프로필이 성립 안 함 (원래 89점 있었음)
작가당 최소 8점 이상인 작가만              → 26명
작가당 최대 12점                           → 295점
Darmstadt Madonna는 강제 포함(pin)          ⚠️ 캡에 걸려 빠졌었다
동점 처리: description 긴 순 → key 오름차순
```

| 축 | 결과 |
|---|---|
| 작품 | **295** (German 124 / Flemish 137 / Dutch 34) |
| 작가 프로필 | **26** (작가당 8~12점 — 프로필 쓰기 충분) |
| 사조 프로필 | **5** (school × 반세기) |
| type 분포 | religious 192, portrait 65, mythological 19, landscape 6, historical 6, 기타 7 |
| description | 중앙값 779자 / p90 2,930 / 최대 6,081 / **1,292자 초과 103점** |

⚠️ **기록해둘 선택 편향 두 가지**

1. **동점 처리를 "description 긴 순"으로 했다.** 그래서 이 전시는 **설명이 잘 붙은 작품 쪽으로 치우쳐 있다**
   — 중앙값이 전체 코퍼스 588자 대비 779자, p90은 1,292 → 2,930으로 뛰었다.
   RAG 코퍼스로는 유리하지만(근거가 풍부), **전체 코퍼스의 대표 표본이 아니다.** 스케일 인덱스와
   숫자를 비교할 때 이 차이를 감안할 것.
2. **religious가 65%다.** 북유럽 르네상스의 실제 구성이라 자연스럽지만, **골드셋을 종교화 질문으로만
   채우지 않도록** 유형 배분을 의식적으로 잡아야 한다.

⚠️ **`German 1450–1499`가 12점뿐**이라 사조 프로필로는 얇다. 사조 축을 school만(3개)으로 묶을지,
반세기 분할(5개)을 유지할지는 프로필 생성 시 결정한다.

## 2. 아키텍처 — 기존 이음새를 그대로 따른다

이 프로젝트는 이미 두 번 같은 패턴을 썼다: `InferenceEngine`(엔진 교체), `ArtworkRecognizer`(인식 교체).
**RAG도 세 번째 이음새로 넣고, `InferenceEngine`과 `LiteRtEngine`은 한 줄도 건드리지 않는다.**

```
Retriever (interface)                     ← 새로 추가할 계약
  ├─ NoopRetriever        RAG off (대조군)
  └─ EmbeddingRetriever   임베더 + 벡터스토어
        ├─ TextEmbedder (interface) → OnnxEmbedder
        └─ VectorStore  (interface) → FlatVectorStore
```

**프롬프트 조립 지점이 핵심 설계 결정이다.**

- ❌ **system 프롬프트에 넣지 말 것.** 시스템 프롬프트는 KV 캐시에 프리필해 재사용하는 구조인데,
  검색 결과는 쿼리마다 달라지므로 **캐시 재사용이 통째로 깨진다.** 두 엔진 모두 해당.
- ✅ **user 턴 앞에 붙인다.** `generateStreaming(prompt, ...)`의 `prompt` 문자열을
  `"[참고 자료]\n…\n\n[질문]\n…"` 형태로 조립. → **엔진 인터페이스 변경 0.**
  이게 TTFT 상승의 정체이자, 우리가 측정해야 할 비용이다.

**인덱스 파일 배치**: 앱 번들(assets)이 아니라 **모델과 같은 `getExternalFilesDir(null)`에 adb push**.
`ModelCatalog` 패턴을 그대로 재사용하면 **인덱스를 바꿔도 재빌드가 필요 없다**(§1-3의 이중 인덱스가
여기에 얹힌다). 최종 배포 시점에만 assets로 옮길지 결정.

### 2-1. 검색 단위 세 종류 — 결정 2

우리 코퍼스에는 **"사조 문서"도 "작가 문서"도 없다.** 있는 건 작품 기록뿐이고
(`title/author/type/technique/school/date/description`), "독일 르네상스 회화란 무엇인가"를 서술한
문서는 존재하지 않는다.

그러므로 청킹의 문제가 뒤집힌다 — **긴 문서를 어떻게 자르나**가 아니라
**흩어진 작은 기록들을 어떻게 모아 검색할 만한 덩어리로 만드나.**

```
인덱스 구성 (전시 기준)
├─ 작가 프로필      ~25 청크    ← 작품 기록을 author로 집계해서 생성
├─ 사조 프로필       ~5 청크    ← school × 시대로 집계해서 생성
└─ 작품 청크       ~350 청크    ← 원본 레코드 (자연 청크)
```

**작가 프로필 예시** (집계로 만든다 — 없던 문서를 생성하는 것)

```
"Hans Holbein the Younger. German school. 1497–1543.
 이 전시에 47점. 주요 유형: portrait 31, religious 12.
 제작 시기 1515–1543. 주요 기법: oil on wood.
 대표작: Darmstadt Madonna(1526), The Ambassadors(1533), ..."
```

⚠️ **통계 사실만 넣고 서술은 최소화할 것.** 숫자·목록은 실제 데이터에서 나오므로 환각이 아니지만,
"이 작가의 특징은…" 같은 서술을 LLM으로 생성해 넣으면 **그 요약 자체가 환각일 수 있고**,
그게 근거 문서로 들어가면 환각이 인덱스에 굳어버린다.

**작품 청크를 버리지 않는 이유** (RAG는 사조·작가용인데 왜 남기나)

1. "이런 분위기의 다른 그림 있어?"는 **작품 단위 의미 검색**이어야 답이 된다. 프로필로는 못 푼다
2. 사조 질문에 답할 때도 LLM은 **구체적 예시**가 있어야 도슨트답게 말한다.
   "당시 독일 회화는 종교화가 많았습니다"보다 "예를 들어 크라나흐의 〈…〉를 보시면"이 낫고,
   그 예시가 환각이 아니려면 실제 레코드가 근거로 들어가야 한다

**청킹 규칙 (작품)**

- **작품 1점 = 자연 청크**다. p90이 1,292자니 **90%는 무분할**, 긴 꼬리만 문단 단위로 2~3분할
- ⚠️ 문장 중간에서 끊지 말 것. 문단·문장 경계로 자른다. 청크가 원래 독립적이라 오버랩은 아마 불필요
- 한 작품이 여러 청크로 갈라져도 **전부 같은 `artwork_id`를 달고 다닌다**

**메타 스키마 (모든 청크 공통)**

```
{ chunk_id, type: "artwork"|"artist"|"movement",
  artwork_id?, artist?, school?, date?, title?, chunk_index, text }
```

⚠️ **`type`별로 검색을 분리해야 한다.** 다 섞어놓고 top-3를 뽑으면 사조 질문에 작품 청크 3개가
올라오는 사고가 난다. 질문 유형에 따라 필터하거나 타입별로 k를 배분한다.

⚠️ **작품 단위 중복 제거.** top-3가 전부 같은 작품의 청크 0,1,2면 근거가 사실상 1개뿐이다.
`artwork_id`로 묶어 다양성을 확보한다.

### 2-2. 검색 언어는 단일 — 결정 3

언어가 등장하는 자리가 셋인데, **통일 대상은 검색 계층뿐이다.**

| 계층 | 처리 |
|---|---|
| 코퍼스(문서) | **영어** (원본 그대로, 번역 없음) |
| **검색 쿼리** | **영어** |
| 사용자 질문 · 답변 | **영어** — LoRA를 영어로 재학습(§5-5 결정 4) |

**결정 4로 언어 변수가 파이프라인에서 통째로 사라졌다.** 근거·질문·답변·검색이 전부 영어라
cross-lingual 처리(LLM 1패스 검색어 추출 등)가 아예 필요 없다.

이유: cross-lingual(한국어 질문 → 영어 문서)은 **미검증 축**이다. 검색이 안 될 때
"임베딩이 나쁜 건지 언어를 못 넘은 건지" 구분이 안 된다. CLAUDE.md의 **한 번에 한 변수** 원칙과 같다.

단일 언어로 두면 Phase 2가 이렇게 단순해진다:

```
Phase 2  — 같은 언어 질문 → 같은 언어 문서
           "우리 코퍼스에서 임베딩 검색이 되긴 하는가"
           안 되면 여기서 접는다 (언어 탓이 아님이 확실)
```

덤: 단일 언어면 다국어 임베더를 쓸 이유가 없다. 같은 크기에서 **단일 언어 전용 임베더가 더 정확하고,
다국어 어휘를 안 실어서 더 작다.** 폰 용량·지연 둘 다 이득.

⚠️ 앱에서 사용자 질문 언어와 검색 언어가 다를 경우의 처리(LLM 1패스 검색어 추출, 메타 필터 우회)는
**Phase 5 이후로 미룬다.** 결정 4가 정해지면 아예 필요 없어질 수도 있다.

## 3. 단계별 로드맵

각 Phase는 **다음 Phase 없이도 단독으로 검증 가능**해야 한다. 특히 Phase 2에서 실패하면 앱 코드는 손도 대지 않는다.

### Phase 0 — 범위 확정 (코드 0줄)
- §0의 표 확정: **RAG가 담당할 질문 유형**과 **기존 lookup이 담당할 유형**의 경계. ✅ (08-13)
- 결정 1~3 확정. ✅ (08-13) / **결정 4(언어)는 미정** — §5-5
- 산출물: 이 문서

### Phase 1 — 전시 큐레이션 + 청킹 + 골드셋 (PC/Colab, 앱 무관)
- **전시 부분집합 확정** — §1-4의 필터로 실제 건수 실측 → 300 근처로 조정. Darmstadt Madonna 포함 확인
- `art_metadata.json` → 청크화 스크립트. **부분집합 파라미터 필수**(§1-3)
- **작가/사조 프로필 생성** — 집계 기반, 통계 사실 위주(§2-1)
- 긴 description(p90 초과) 분할 규칙 결정
- **골드셋 30~50문항**: 질문 + 정답 `chunk_id`/`artwork_id` 집합.
  ⚠️ 질문 유형(작품/작가/사조)별로 고르게 배분할 것 — 타입별 검색 분리를 평가하려면 필요하다.
  ⚠️ `docent_seeds.jsonl`(LoRA 학습셋)과 **겹치지 않게** 만들 것 — 겹치면 암기 검증이 된다
- 산출물: `datasets/rag_chunks.jsonl`, `datasets/rag_goldset.jsonl`

### Phase 2 — 오프라인 검색 품질 검증 (PC/Colab) ★ 게이트
**여기서 recall@k가 안 나오면 앱 작업은 시작하지 않는다.**
- 후보 임베더 2~3종 비교. **결정 4가 정해진 뒤 그 언어의 단일 언어 모델 중에서 고른다**
- 지표: **Recall@1/3/5, MRR**(블로그도 이 지표로 골랐다). **질문 유형(작품/작가/사조)별로 나눠 볼 것**
- 후보 개선책 벤치: `query:`/`passage:` 프리픽스(e5 계열 필수), 메타데이터 필드 결합 방식(§5-5 #1),
  타입별 k 배분, **메타데이터 필터 + 벡터 검색 하이브리드**(예: "홀바인 다른 작품" = `author` 필터가 임베딩보다 정확)
- ⚠️ **전시(~380청크)와 전체(~27,500청크) 양쪽에서 잰다.** 전시에서만 재면 게이트가 너무 헐겁다
- 산출물: 비교표 + 임베더 1종 확정

### Phase 3 — 온디바이스 임베더 (앱, 단독 검증)
- ONNX 내보내기 + INT8 양자화(`optimum`), 토크나이저는 `onnxruntime-extensions`로 ONNX 그래프화.
  → 블로그가 이미 뚫어놓은 경로. ⚠️ **토크나이저가 이 단계의 최대 난관**이다(Android에 HF tokenizers가 없다).
  텍스트 → 토큰 ID 변환이 PC와 폰에서 1비트라도 다르면 다른 벡터가 나오고, 코사인 유사도가 통째로 무의미해진다
- 런타임 선택: **ONNX Runtime Android 권장.** 프로젝트에 `tensorflow-lite`가 이미 있지만 그건
  향후 이미지 인식(`ArtworkRecognizer`)용이고, 임베더의 TFLite 변환은 검증된 경로가 아니다
- 검증: **PC 임베딩 vs 폰 임베딩의 cosine 일치도 > 0.999**. 여기서 어긋나면 이후 전부 무의미
  (완전 일치가 아닌 이유: 부동소수점 연산 순서, x86 vs ARM, INT8 양자화)
- 측정: 쿼리 1건 임베딩 지연(ms), APK/모델 용량 증가

### Phase 4 — 온디바이스 벡터스토어 (앱, 단독 검증)
- 인덱스 파일 로드 + brute-force cosine 전수 스캔. L2 정규화해 두면 내적 = 코사인이라 곱셈+덧셈뿐
- ⚠️ sqlite-vec는 ARM64 Android 바이너리가 없다(블로그가 겪은 지점) — **직접 구현이 기본안**.
  우리는 읽기 전용 전수 스캔뿐이라 **flat 바이너리 + 메타 JSON**이 SQLite BLOB보다 단순하고 빠를 수 있다(§5-5 #2)
- ⚠️ **벡터 행 순서와 메타 순서가 곧 연결이다.** 어긋나면 엉뚱한 작품을 근거로 답한다 — 그것도 **에러 없이 조용히**.
  헤더에 청크 수·차원·임베더 이름을 기록해 로드 시 검증한다(`IndexCatalog`)
- 전시/전체 양쪽 전수 스캔 지연 실측. 느리면 int8 양자화 → 그래도 느리면 그때 ANN 검토(예상: 불필요)
- 측정: **retrieval latency(ms), 인덱스 로드 시간, `mem_peak` 증가분**

### Phase 5 — 파이프라인 결합 (앱)
- `Retriever` 이음새 추가, `InferenceScreen`이 생성 직전 `retrieve(query)` → 프롬프트 조립
- **`NoopRetriever`로 RAG off를 1급 시민으로** 둘 것 — 대조군이 코드 경로를 공유해야 공정하다
  (자동화 경로를 따로 만들지 말라는 프로젝트 원칙과 같은 이유)
- top-k와 컨텍스트 예산을 상수로: k=3 시작, 청크 평균 588자 ≈ 150~200토큰 → **k=3이면 +600토큰 내외**.
  ⚠️ `n_ctx=1024`는 llama.cpp 쪽 값이다. LiteRT-LM 경로의 실제 컨텍스트 한계를 **먼저 확인**할 것 —
  현재 시스템 프롬프트만으로 이미 ~420토큰이다
- 질문 언어 ≠ 검색 언어인 경우의 처리는 결정 4 확정 후에 다룬다(§2-2)

### Phase 6 — 벤치 통합 (앱 + 스크립트)
- `BenchmarkRecord.rag` 필드가 **이미 null로 비어 있다.** 그 자리를 채운다:
  `rag = {"on":true,"embedder":…,"k":3,"index":"exhibition-300","chunks":380}` 같은 self-describing 값.
  ⚠️ **어느 인덱스로 쟀는지를 반드시 넣을 것** — 이중 인덱스(§1-3)라 없으면 나중에 구분이 안 된다
- 새 지표 추가: `retrieval_ms`, `embed_ms`, `retrieved_ids`(재현·감사용)
- `AutoRunRequest`에 `-e rag on|off`, `-e index <name>` 추가 → **재빌드 없이 A/B**.
  `BenchSignal`에 실패 사유(`INDEX_NOT_FOUND`, `EMBEDDER_FAILED`) 추가 ⚠️ 안 그러면 스크립트가 영원히 기다린다
- ⚠️ **한 번에 한 변수**: 모델은 LoRA본으로 고정하고 `rag`만 토글. 임베더·k·청킹·인덱스를 동시에 바꾸지 말 것
- 예상 결과(가설로 미리 적어둔다): `prompt_tokens` ↑↑, `ttft` ↑, **`engine_tok_s`는 변화 없음**(decode는 무관).
  이게 안 맞으면 어딘가 잘못된 것

### Phase 7 — 품질 평가
- 재료는 이미 자동 수집된다 — `responses.jsonl`(`run_id`로 조인). ⚠️ 지금 스키마에 `model`/`engine`을
  일부러 뺀 것과 같은 이유로 **`rag` 여부도 응답 파일에 넣지 말 것**(블라인드 채점)
- 축 3개: **groundedness**(코퍼스에 근거가 있는가) / **환각률**(§CLAUDE.md의 "암굴의 성모 = 카라바조" 류 오류가 줄었는가) /
  **도슨트 화법 유지**(LoRA 효과가 컨텍스트에 파묻히지 않았는가)
- 4셀 비교가 최종 그림: `{LoRA on/off} × {RAG on/off}`

## 4. 주요 리스크

| 리스크 | 왜 위험한가 | 대응 |
|---|---|---|
| **토크나이저 이식** | Android에 HF tokenizers가 없다. Phase 3의 최대 난관 | `onnxruntime-extensions` ONNX 그래프화(블로그 검증됨), PC 대조로 조기 검출 |
| **파생 프로필의 환각** | 집계 요약을 LLM으로 쓰면 환각이 **인덱스에 굳는다** | 통계 사실만 기재, 서술 최소화(§2-1) |
| **전시 축소로 게이트가 헐거워짐** | ~380청크면 웬만한 임베더도 통과 | Phase 2를 전체 코퍼스에서도 함께 측정 |
| **타입 혼재 검색** | 사조 질문에 작품 청크만 올라오는 사고 | `type` 필드 + 타입별 k 배분, 골드셋을 유형별로 배분해 검출 |
| **인덱스 행 순서 어긋남** | 엉뚱한 근거를 **조용히** 인용 | 헤더에 청크 수·차원·임베더명 기록, 로드 시 검증 |
| **컨텍스트 예산 초과** | 시스템 프롬프트 ~420토큰 + 검색 600토큰 | k와 청크 길이로 조절, LiteRT 실제 한계 선확인 |
| **앵무새 악화 / 화법 붕괴** | LoRA 효과를 RAG가 덮을 수 있음 | 4셀 비교로 분리, 프롬프트에서 "인용이 아니라 설명" 지시 |
| **TTFT 악화** | 온디바이스 CPU에서 prefill이 이미 병목(~3.6s) | 비용을 숨기지 말고 **측정해서 보고**. 이게 논문의 trade-off 결과물이다 |
| **GPU 부재** | 활성값 fp32라 CPU 고정(2026-08-01) | RAG는 GPU와 독립. 다만 절대 지연은 CPU 기준으로 읽을 것 |

⚠️ `PromptAssembler`는 **부작용 없는 순수 함수**로 둘 것. 프롬프트 조립이 엔진·파일 I/O에 엉키면
"이 컨텍스트로 뭘 넣었는지"를 나중에 재현할 수 없다.

### 5-5. 착수 전에 정해야 할 설계 결정 (코드 0줄)

#### ★ 결정 4 — 파이프라인 전체를 **영어로 통일** ✅ 확정 (08-13)

**해야 할 일**: `docent_seeds.jsonl` 100건 영어 재작성 → LoRA 재학습 → `.litertlm` 재변환.
⚠️ **재작성 시 작품·문답 구조는 그대로 두고 언어만 바꿀 것** — 그래야 한국어본과의 차이가 '언어'
하나로 통제되고, 화법 전이 실패(2026-08-02 관측)가 언어 탓인지 아닌지 갈린다. 기계 번역은 안 된다
(영어 도슨트 화법은 한국어 화법의 직역이 아니다).
⚠️ 대조군 `.litertlm`은 **재변환 불필요** — 베이스 모델은 언어 무관이라 기존 파일을 그대로 쓴다.

아래는 확정 전에 비교한 기록이다(왜 영어를 골랐는지의 근거).

§2-2에서 "검색은 단일 언어"까지는 정했다. **어느 언어인가**가 남았고, 이건 LoRA에 직접 걸린다.

배경: LoRA는 한국어 도슨트 문답 100건으로 학습했다. CLAUDE.md 2026-08-02 기록 —
영어로 재던 시절 6건에서 길이·형식·톤은 전이됐지만 **도슨트 화법(관찰 유도)이 영어 답변 어디에도 없었다.**
화법은 출력 언어에 붙어 있다.

현재 벤치 누적본(96건) 구성:

| 프롬프트 | LoRA본 | 대조군 |
|---|---|---|
| 영어 | 33 | 33 |
| 한국어 | 15 | 15 |

⚠️ **LoRA를 재학습하면 LoRA 레코드 48건이 전부 구형이 된다**(대조군 48건은 살아남는다 — 베이스 모델은 안 건드리므로).
"영어로 되돌리면 영어 33건을 되찾는다"는 이득은 **없다** — 그건 한국어로 학습한 LoRA로 잰 값이다.

| | **영어로 통일** | **한국어로 통일** |
|---|---|---|
| 학습셋 100건 | ⚠️ **영어로 재작성** — 기계 번역 불가(화법은 직역이 아님) | ✅ 그대로 |
| LoRA 재학습 | ⚠️ 필요 | ✅ 불필요 |
| `.litertlm` 재변환 | ⚠️ 9.5GB 병합 → litert-torch, RAM 병목·High-RAM 런타임 | ✅ 불필요 |
| 코퍼스 | ✅ 그대로 (영어) | ⚠️ 전시 300점 description **자동 번역**(Colab 배치) |
| 임베더 | 영어 전용 (선택지 넓음) | `multilingual-e5-small-ko-v2` — **블로그가 검증한 경로** |
| 사람이 하는 일 | **100건 창작 (며칠)** | 번역 스크립트 1개 |

- **한국어 통일의 이점**: 재학습 0. 코퍼스 번역은 결정 1(300점 축소) 덕에 **갑자기 싸졌다** —
  21,382점이면 못 할 일이었다. 그리고 한국어 코퍼스 + 한국어 질문은 **블로그 사례와 정확히 같은 설정**이라
  cross-lingual이라는 미검증 축이 통째로 사라진다
- **한국어 통일의 대가**: LoRA 학습 조건이 '영어 근거 → 한국어 답변'에서 '한국어 근거 → 한국어 답변'으로
  바뀐다. 다만 화법은 **출력 언어**에 붙어 있고 그건 그대로 한국어다 — 영어로 답하게 만드는 것보다
  훨씬 약한 변화다. 번역 시 **원문을 함께 보관**해두면 되돌릴 수 있다
- **영어 통일의 이점**: 코퍼스가 원본 그대로라 번역 오류가 근거에 섞이지 않는다
- **판단 기준**: **이 앱은 누구에게 말하는가.** 국내 전시 시나리오면 관람객 언어가 답변 언어다.
  발표·논문이 영어권이고 데모도 영어여야 한다면 재학습 비용을 내는 게 맞다

#### 나머지 결정

1. **임베딩 대상 텍스트 포맷** — description만? `title/author/school`까지 합친 문자열?
   ⚠️ **임베더는 자기가 본 문자열만 안다.** description 본문에 작가명이 없으면 "홀바인" 질문이 안 걸린다.
   메타데이터를 본문 앞에 붙이는 쪽이 유력하지만 Phase 2에서 실측할 것
2. **인덱스 저장 형식** — 블로그는 SQLite BLOB. 우리는 읽기 전용 전수 스캔뿐이라
   **flat 바이너리 + 메타 JSON**이 더 단순하고 빠를 수 있다
3. **k와 컨텍스트 예산** — k=3 시작. 타입별 배분(작품 2 + 프로필 1?)도 함께
4. **인용 표기 방식** — 답변에 근거 작품을 어떻게 드러낼지(블로그의 "인용 링크"에 해당)
5. **메타데이터 필터 하이브리드를 쓸 것인가** — "홀바인 다른 작품"은 `author` 필터가 임베딩보다 정확하다.
   전시가 300점이면 작가가 20~30명뿐이라 **매핑 테이블 방식이 현실적으로 가능해졌다**

## 6. 하지 않을 것

- 서버 임베딩 API(블로그의 FastAPI 단계) — **인덱스 빌드는 Colab에서 오프라인 배치 1회**면 된다. 상시 서버 불필요.
- ANN/HNSW — 전시 규모에선 명백히 불필요하고, 전체 27.5k에서도 전수 스캔이 충분하다. 실측이 느릴 때만 검토.
- 재랭킹(cross-encoder) — 온디바이스에서 2단계 모델은 과하다. Phase 2에서 recall이 아깝게 모자랄 때만.
- 기존 작품 lookup을 임베딩 검색으로 대체 — **정확한 키가 있는데 근사 검색으로 바꾸는 건 퇴보다.**
- 임베더 파인튜닝 — 질문-정답 쌍 수천 건이 필요하다. 기성 모델을 **고르는** 것까지가 Phase 2의 범위.
- cross-lingual 검색 — 결정 3으로 배제. 결정 4가 정해지면 완전히 사라진다.
